## Where public sources contradict the model

### P29: Retain the default maxPoolSize unless workload context justifies tuning, rather than requiring explicit pool parameters for every application.

- **The model believed:** Set maxPoolSize and waitQueueTimeoutMS explicitly so concurrent Flask requests cannot create unbounded database connection pressure or wait indefinitely for a connection. (knowledge of `mongodb`)
- **The source says:** Retain the default maxPoolSize unless workload context justifies tuning, rather than requiring explicit pool parameters for every application.
- **Source:** [documentdb-connection](https://github.com/Azure/documentdb-agent-kit/blob/main/skills/connection/SKILL.md)

### P35: Use a separate read-only secondary runtime user but account for native readAnyDatabase permissions being cluster-wide rather than catalog-database or collection scoped.

- **The model believed:** Give the runtime database identity only the catalog read permissions it needs, and use a separate provisioning identity for seeding and index creation. (knowledge of `mongodb`)
- **The source says:** Use a separate read-only secondary runtime user but account for native readAnyDatabase permissions being cluster-wide rather than catalog-database or collection scoped.
- **Source:** [Azure DocumentDB service limits and quotas reference](https://learn.microsoft.com/azure/documentdb/limitations#authentication-and-access-control-role-based-access-control)
